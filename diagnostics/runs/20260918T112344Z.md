`planner.SYSTEM_PROMPT` section 1 lists all 16 DOMAINS as **bare token names with no
definitions**, immediately followed by "If a question could plausibly touch several, LIST
THEM ALL. Widening is correct; narrowing is a failure."

So the widest lever in the taxonomy carries the loosest semantics. Against
`HARD_CONTEXT_CEILING = 150_000` approx (S135), one `technique_method` selection admits
**99.2% of the entire ceiling**. Q1 of the S136 dogfood sits at 254,836 est-real with ~100
tokens of margin.

**The consequence is not cost, it is FALSE SILENCE.** The build plan's standing doctrine is
"honest silence beats confident-wrong -- a question the material cannot answer for THIS
person gets a stated refusal." A ceiling refusal is different in kind: the material CAN
answer it, and the system declines because a mis-scoped tag ate the budget. That is a
third failure class the doctrine does not sanction.

**It is not a new law.** It is Working Style #22 (S95 vocabulary contract: "every rule
trigger token MUST exist in the emitted vocabulary; mismatch = silent miss") in the
OVER-FIRE direction. #22 catches silent misses; P-030 catches silent over-fire.

**The house style already exists and the planner is the deviation.**
`agent/context_classifier.py::_SYSTEM_PROMPT` glosses every term in all four of its closed
vocabularies (`retrieval_profile`, `context_order`, `needs_required`, `needs_enriching`)
with explicit `ONLY when` scope guards. `planner.py` -- newer and far more load-bearing --
does not.

## 3. WHY NO THRESHOLD (C' withdrawn -- the correction to my own proposal)

I proposed dropping units contributing <=2 segments, sized at 46,263 tokens. Sulabh
challenged the hardcoding. Verification killed the proposal:

- `planner.payload_tokens()` = `sum(units[].tokens)` + `sum(segments[].tokens where kept)`
  -- two additive channels; the `units` channel is all-or-nothing (`kind="whole_chapter"`).
- Segmentation coverage: **98 of 100 units have segment-level tags** (235,983 / 242,571
  tokens). Of the 45 `technique_method` units, **0 are unsegmented.**
- Therefore the 46,263 figure was CHAPTER SIZES from the tag artifact, **not tokens the
  payload ships.** Every one of those chapters is segmented, so
  `filter_segments_by_domain` is already the operative narrowing -- and it fails SAFE by
  the S124 lock (untagged / unknown-id / `unfittable` segments are KEPT, never dropped).
- A `<=N` floor would therefore delete segments that filter already vetted: pure answer-
  quality loss for zero measured gain.

**Answer to "what is the max limit in the worst case?"** -- there is no safe constant, and
that is the finding rather than a bigger number. The worst case for a correct answer is a
chapter where the one matched segment's meaning depends on a qualifying verse elsewhere in
that chapter (BPHS routinely places the "unless" three verses later). For that case the
safe floor is ALL segments. A rule whose worst case requires "all" cannot be a count.

If measurement later shows real waste, the replacement is STRUCTURAL, not numeric: a unit
enters the payload as its segments where segmentation exists, and whole only where it does
not. Same direction as the already-ratified S135 close ("segment-split, NOT whole") for
yoga augmentation.

**Still unverified, and this is what task C now is:** S130 section 6 records "23 of 81
selected units contribute zero segments and are carried whole", which CONTRADICTS the
measurement above. Either it means something other than what it says, or the builder
promotes segmented units to `whole_chapter` regardless. This cannot be resolved from the
tag artifact plus `data/career_payload_bphs.json` (builder `cp-1.0`, generated
2026-09-05, i.e. S124-era and pre-dating current tagging). It needs instrumentation of a
real run. Recorded as a NOTE inside the P-030 row so a future session does not resurrect
the threshold.

## 6. PROCESS FAILURE IN THIS RUN -- DISCLOSED

**I broke SURGICAL EDITS on the first write of `KNOWN_PATTERNS.md` and corrected it.**

`KNOWN_PATTERNS.md` is **CRLF** (100 CRLF line endings); `CLAUDE.md` is **LF**. My first
edit read the file with Python's default universal-newline translation and wrote it back
with `\n`, which **converted the entire file from CRLF to LF** -- a whole-file change
masquerading as a one-line insert. `diff -u` exposed it: 204 diff lines for what should
have been 1. That version WAS briefly written to disk.

Corrected by re-reading the pristine staged original with `newline=''`, inserting the row
with an explicit `\r\n`, and re-writing with `newline=''`. Verified: 101 CRLF endings
(100 original + 1 inserted), diff back down to a single `+` line.

**Generalisable lesson, worth its own row if it recurs:** this repo has MIXED line endings
across files. Any programmatic edit must preserve the target file's existing endings
(`newline=''` on both read and write), and the acceptance check is that `diff -u` shows
only the intended lines -- never trust the edit, check the diff. Not filed as a P-row this
session: one occurrence, and the project's own rule is "do NOT add a row speculatively;
add one when a real failure is observed twice."
