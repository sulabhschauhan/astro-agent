### Column detection method

Rasterize the page (already done for OCR); run `pytesseract.image_to_data`
on the same image (`eng+hin`, `--psm 3`), group word boxes by
`(block_num, par_num, line_num)`, take `min(left)` per line as that line's
x0. Sort all line-x0 values; find the single largest gap; call the page
**BIMODAL** iff that gap exceeds 15% of image width AND each side holds at
least 20% of total lines, else **UNIMODAL**. Diagnostic heuristic, not a
tuned production threshold.

**Result: all 10 sampled Phaladeepika/Saravali pages are UNIMODAL.** Gaps
found were small (2.7%–13.0% of image width) even where the two "sides" were
close to evenly split in line count (e.g. Saravali p161: 16 vs 15 lines,
4.9% gap) — read most plausibly as verse-vs-prose indentation variance within

clean, wide dead zone between two line-count-balanced groups — a
qualitatively different, much stronger signal.

## (d) PART 4 — Source verification

### 4a. `strip_devanagari()` guard + operation (`ingestion/chunker.py:60-76`)

```python
def strip_devanagari(text: str) -> str:
    """
    Remove Devanagari content from OCR text before chunking.
    - Lines where >50% of non-whitespace characters are Devanagari are dropped entirely.
    - Remaining Devanagari characters are stripped from surviving lines.
    """
    cleaned_lines = []
    for line in text.splitlines():
        non_ws = [c for c in line if not c.isspace()]
        if not non_ws:
            cleaned_lines.append(line)
            continue
        devanagari_count = sum(1 for c in non_ws if "ऀ" <= c <= "ॿ")
        if devanagari_count / len(non_ws) > 0.50:
            continue  # drop line
        cleaned_lines.append("".join(c for c in line if not ("ऀ" <= c <= "ॿ")))
    return "\n".join(cleaned_lines).strip()
```

Guard: `devanagari_count / len(non_ws) > 0.50` per line. **Above** threshold:
the whole line is dropped (`continue`). **Below or equal** threshold: the
line survives, but every individual Devanagari codepoint in it is stripped
out character-by-character (`"".join(c for c in line if not (...))`) — so a
surviving line still ends up with **zero** Devanagari characters in it either
way. The 50% threshold only decides *whole-line drop vs. partial character
strip*, never "keep some Devanagari."

### 4d. Can a chunk reach `translator.py` still carrying ≥0.25 Devanagari?

**Yes — via one specific code path.** `chunker.chunk_page()`
(`ingestion/chunker.py:159-195`) has three branches:

- `page_type == "diagram"` **and empty text** → pass-through unchanged, no
  enrichment (never reaches translator with meaningful text anyway).
- `page_type == "diagram"` **and filled text** (lines 172-180) → enriches
  `topic`/`language`/`word_count` but **does not call `strip_devanagari()`**.
- `"text"` / `"mixed"` (lines 182-195) → **always** calls
  `text = strip_devanagari(text)` before producing sub-chunks, which per 4a
  zeroes out all Devanagari codepoints in every surviving line.

So: any `"text"`/`"mixed"` page is Devanagari-scrubbed to exactly 0.0 fraction
before it can reach `data/all_chunks.json` (translator's input). But a
`"diagram"` page whose `text` was filled by `image_extractor.py`'s GPT-4o
vision call (which can legitimately return Devanagari script — the extraction
prompt asks for "Rashi (zodiac sign) names in Sanskrit and/or English") skips
`strip_devanagari()` entirely and could carry ≥0.25 Devanagari fraction
straight through to `translator.py`. This is a real, source-verified gap in
the "chunker always sanitizes before translator" assumption — narrow (only
the diagram+filled-text path), not exercised in this probe (no such chunk was
observed with populated Devanagari text in the current corpus), but real.
